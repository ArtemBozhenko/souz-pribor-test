# Тестовое задание: AI-помощник для подготовки товарных описаний

Вакансия: AI/LLM-разработчик, Союз-Прибор (https://hh.ru/vacancy/139067096).
Срок сдачи: 08.11.2026. Сдать в чат hh или на ermoshinais@souz-pribor.ru (Ермошина Инна Сергеевна).
Оригинал: https://drive.google.com/file/d/1CcfOkv2K2CG8k7Ys1X430QRH_ZR-IGT6/view
Ориентировочное время: 2–4 часа.

## Цель

Прототип сервиса: по входным данным о контрольно-измерительном приборе создаёт черновик карточки товара для B2B-интернет-магазина.
Проверяют работу с LLM API, структурирование техданных, качество промптов, практичность результата для контент-менеджера.

## Входные данные

По двум товарам: название, производитель, краткие характеристики, текстовое описание или фрагмент паспорта.
В PDF данных по двум товарам нет, только пример:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

## Что делает сервис

1. Принимает данные о товаре в JSON или через простую веб-форму.
2. Передаёт данные в LLM через API.
3. Формирует черновик карточки товара.
4. Возвращает результат в удобном для копирования виде: JSON, Markdown или текст.
5. Если данных недостаточно, сообщает, какие поля отсутствуют или требуют уточнения.

## Результат по каждому товару

- SEO-заголовок до 70 символов.
- SEO-описание 800–1200 символов.
- Структурированный список ключевых характеристик.
- 3–5 поисковых запросов.
- Commercial-блок для менеджера: кому подходит прибор и какие задачи решает.

## Технические требования

- Python или JavaScript/TypeScript.
- API одной LLM на выбор.
- API-ключ не в коде: переменные окружения или конфиг в .gitignore.
- Корректная обработка ошибок API, пустых полей, некорректного JSON.
- Модель не выдумывает характеристики: все технические значения только из входных данных.
- Отсутствующая характеристика помечается «данных нет».

## Критерии оценки

Не объём кода, а качество и применимость:
- корректность, читаемость, структура кода;
- качество промпта: точность, устойчивость, соответствие задаче;
- отсутствие выдуманных характеристик;
- обработка неполных и некорректных данных;
- готовность результата для контент-менеджера;
- качество README и простота запуска.

## Ограничения

Не нужны CMS, админка, БД, деплой, векторная база. Достаточно локального прототипа. Если не укладываемся в 2–4 часа, делаем MVP и описываем улучшения.
